# 插件

> **兼容性与责任声明：** 插件系统沿用 TREK，仅为兼容性而保留。Tourism-Team（TT）不对第三方插件的可用性、正确性、安全性或持续兼容性作保证。启用前请逐项审查，并自行承担插件访问数据的责任。

插件让任何人都能**在不改动 Tourism-Team 源代码的前提下**，为自托管的 Tourism-Team 实例
扩展新功能 —— 一个仪表盘小组件、一个完整页面、一个照片/日历集成。它们由第三方开发，
从公开注册表分发，并由实例所有者自行决定是否安装。

> [!IMPORTANT]
> **插件运行的是任意代码，虽有隔离但确实在运行。** 每个插件都在自己的沙箱化子进程中
> 运行，且只拥有你批准的权限。Tourism-Team 不维护、不审计、也不为社区插件承担责任。
> 只授予你信任该插件对你的数据所拥有的访问权限，并优先选择标记为 **已审核** 的插件。

## 插件类型

插件在其清单中声明一个 `type`，它决定插件出现在哪里：

| 类型 | 显示位置 | 典型用途 |
|---|---|---|
| **widget** | 在仪表盘上 —— 侧栏中、作为登机牌风格的主视觉浮层（`slot: "hero"`），或停靠进行程规划器内的**详情面板**：打开的地点（`slot: "place-detail"`）、日程（`slot: "day-detail"`）或预订（`slot: "reservation-detail"`） | 一览式的信息，如航班状态或天气；详情面板小组件的作用范围仅限你打开的那一个地点/日程/预订 |
| **page** | 作为顶部导航中的一个独立条目 | 一个完整、自成一体的工具 |
| **trip-page** | 作为**每个行程规划器内部**的一个标签页（与计划 / 交通 / 文件并列），作用范围是当前打开的旅行 | 一次针对一次旅行工作的工具 |
| **integration** | 不显示在任何可见位置 —— 通过钩子注册进 Tourism-Team（例如照片来源、日历来源或**通知渠道**） | 把数据喂给 Tourism-Team 已有的功能 |

### 通知渠道

`integration` 插件可以新增一整个**通知渠道** —— Gotify、Pushover、Telegram，任何能接收消息的东西
—— 与 Tourism-Team 内置的邮件、webhook 和 ntfy 并列。

一旦你安装并激活这样的插件，它的渠道就生效了 —— **管理 → 通知** 中没有单独的开关，
那里只开启内置的邮件、webhook 和 ntfy 渠道。它会立即出现在每位用户的
**设置 → 通知** 矩阵中，作为一个新列，而每位用户在该插件自己的设置页面上提供自己的凭据，
并逐事件选择他们想要推送的内容 —— 与内置渠道完全一样。

对于插件渠道，有两条保证特别成立：

- **它以用户为范围。** 仅管理员的的事件（如*有新版本可用*）始终通过你内置的管理员渠道发出，
  绝不会走插件的渠道。
- **插件永远看不到任何人的旅行。** Tourism-Team 会*先*把通知渲染好 —— 使用收件人的语言、
  深链接也已构建完毕 —— 然后再交给插件。插件收到的是那条已完成的消息，加上该用户
  为其服务提供的自己的凭据，除此之外什么都没有。它不会获得操作用户，因此其他插件所用的
  那些读取旅行的 API 对它一律拒绝。

### 插件设置操作

插件可以在**它自己的设置表单上放置按钮** —— 一个「测试连接」、一个「立即同步」、
一个「清除缓存」。每个按钮声明一个 `scope`，它决定按钮落在哪里以及由谁运行：

- **`scope: "user"`**（默认值）—— 按钮位于 **设置 → 插件** 下，
  在该插件的字段下方，并以**点击它的那个用户**的身份运行，因此「测试连接」检查的是
  *他们的*凭据，永远看不到别人的。
- **`scope: "instance"`** —— 按钮位于 **管理 → 插件 → ⋯ → 实例设置** 中，
  与它所操作的实例范围字段放在一起。它以点击的**管理员**身份运行 —— 在管理后台中呈现，
  但不具有管理员特权 —— 在插件**处于激活状态之前保持禁用**（「激活插件以运行其操作」），
  并且会在触发前保存已编辑的表单，因此该操作看到的就是你正在看的配置。

Tourism-Team 会拒绝插件未在其清单中声明的任何操作，而作用域由每个按钮提交到的路由固定：
用户标签页的操作永远无法从管理员对话框触发，实例操作也永远不会出现在任何人的设置页面上。

### 插件的 MCP 工具

插件（任何类型）都可以在 **Tourism-Team 自己的 MCP 服务器上发布工具**，这样用户已连接到
Tourism-Team 的 AI 助手就能调用它 —— 在清单中声明（`capabilities.mcpTools`），置于
**`mcp:tools`** 权限之后，两者都属于你在安装时同意的内容。有三条保证：

- **在它存在之前你就能看到其表面。** 管理 → 插件 会准确显示某个插件将宣传哪些
  工具（它们以 `plugin_<id>_<name>` 的形式出现在助手中），而激活、停用、更新、重新信任或
  卸载某个插件 —— 或者关闭它所依赖的某个扩展 —— 都会关闭已打开的助手
  会话，从而使该表面被重新读取。
- **工具调用以发起请求的用户身份运行。** 主机从助手的会话中绑定用户 —— 插件永远无法
  自行指定 —— 因此每一次读取都像插件正常的 API 调用一样做成员校验，而
  `mcp:tools` 授权本身不解锁任何数据：该工具只能做插件的*其他*已授权限
  所允许的事。
- **助手必须明确选择加入。** OAuth 客户端只有携带 **`plugins:use`** 权限范围才能触及插件工具，
  而该范围从不默认授予 —— 用户需要在同意屏幕上明确批准它。

### 行程页面插件：位置与标签页接管

**trip-page** 插件通常把它的标签页添加在规划器内置标签页*之后*。
如果它需要更显眼的位置 —— 或者想取代它所替代的某项功能 —— 它的清单可以通过
`capabilities.tripPage` 来塑造标签栏：

- **`position`** 把插件的标签页固定在首选的插槽上（从 0 开始的索引），
  而不是追加在末尾。
- **`replaces`** 列出插件激活期间要**隐藏**的核心规划器标签页 ——
  例如一个取代内置预订或文件视图的插件，可以占据那个标签页的位置，而不是
  坐在它旁边。**计划** 标签页永远无法被替代：
  一次旅行始终保留其规划器视图，因此插件可以接管个别标签页，而永远无法接管整个旅行。

隐藏的标签页会在插件被停用或移除的那一刻恢复 —— 接管只在插件开启期间持续。

## 启用插件

插件系统**默认开启** —— 运行时和 **管理 → 插件**
标签页开箱即用。已安装的插件仍然必须逐个激活，因此在你自己打开某个具体插件之前，
不会有任何第三方代码运行。

要关闭整个系统，请把环境变量设为 `false` 并重启：

```yaml
environment:
  - TREK_PLUGINS_ENABLED=false
```

关闭后，**管理 → 插件** 标签页会显示一条「已关闭
（TREK_PLUGINS_ENABLED）」横幅，且不会有任何东西运行。已安装的插件仍留在磁盘上，
处于停用且无害的状态，直到你重新开启该系统。

## 隔离模型 —— 插件能做什么、不能做什么

每个处于活动状态的插件都作为一个**独立的操作系统进程**运行，在 Node 的
权限模型（`--permission`）下启动，文件系统读取范围仅限它自己的代码：

- 它**无法**访问 `JWT_SECRET`、数据库连接或任何 Tourism-Team
  机密 —— 那些东西根本不被它的进程所触及。
- 它**不能**打开 Tourism-Team 自己的数据库（`server/data/travel.db`，或在容器中为
  `/app/data/travel.db`）、写文件、派生（spawn）子进程、使用
  工作线程，或加载原生插件。它自己的数据存放在一个单独的 SQLite 文件中，
  只能通过 Tourism-Team 访问。
- 它只通过内部 RPC 通道与 Tourism-Team 通信，而 Tourism-Team 只
  响应插件清单**声明且你批准**的能力。
  未授权的调用会被拒绝，而不仅仅是被忽略。
- RPC 通道本身**与插件代码隔绝**：尽管
  插件运行在一个派生进程中，它的原始 IPC 原语（`process.send`、
  `process.on('message')`）会在其代码加载之前被撤销 —— 正如
  `process.binding` 一样。因此插件既无法伪造主机消息（伪造其路由
  表、冒充另一个请求的身份），也无法窃听其他进行中的
  请求。每一次交互都被强制走经过能力校验的 SDK。
- 页面/小组件的界面运行在一个**封闭的浏览器框架**中，它读不到
  你的会话 Cookie，也无法触及周围的 Tourism-Team 页面。
- 如果插件崩溃、挂起或内存耗尽，只有*它*的进程会死亡 ——
  Tourism-Team 继续运行，并且可以重启或停用它。

这意味着你批准的权限列表是一条**真实的边界**，而不是一个标签。
它限定的是插件能触及*什么*，而不是它在某个授权范围内的意图：一个你让它读取旅行
**并且**访问某台主机的插件，可以把那些旅行发送到那里。每个权限究竟授予了什么，见
[[插件权限|Plugin-Permissions]]。

## 管理 → 插件 面板

一个单独的面板，左上角有 **已安装 / 发现** 分段切换，
外加一条工具栏：

- **搜索** —— 按名称/描述（在发现中还按作者）筛选当前列表。
- **类型**筛选 —— 全部类型 / 小组件 / 集成 / 页面 / 行程页面。
- **状态**筛选（仅已安装视图）—— 全部 / 已激活 / 已关闭 / 有可用更新 / 错误。
- **排序** —— 名称 / 最近更新，已安装中另有**优先显示有更新的**，发现中另有**下载最多**。
  切换视图时，特定于视图的选项会回退到名称。
- **上传** —— 从 `.zip`/`.tar.gz` 手动加载一个插件（见[安装插件](#installing-a-plugin)）。
- **重新扫描** —— 重新发现磁盘上的插件目录**并**强制拉取
  远程注册表，绕过 30 分钟的服务器缓存和 GitHub 的 CDN，使一个
  刚发布的插件（或更新）立即出现，而不是要等上最多约 35
  分钟（见[安装插件](#installing-a-plugin)）。

每个已安装的行都显示一个图标磁贴，带一个**健康状态圆点**（绿色 = 已激活，
蓝色脉冲 = 启动中，红色 = 错误，琥珀色 = 已禁用/不兼容，淡色 = 未激活）、
名称和版本、适用时的**已审核**盾牌、手动上传插件的**手动加载**标签
（见[安装插件](#installing-a-plugin)），以及
由其声明权限推导出的**能力标签** —— 「读取你的旅行」、
「读取你的费用」/「添加费用」、「仪表盘小组件」、「实时更新」、
「提供照片」、出站主机等等 —— 因此无需打开任何东西就能看清插件真实的触及范围。

## 安装前审查插件

在**发现**中，点击任何卡片即可打开其**详情模态框**。这里是你
在插件触及你的实例*之前*审查它的地方。它会获取插件的实时
清单（在所审核的 commit 上），并展示：

- **它能访问什么** —— 以平实语言表述的、由权限推导出的能力。
- **连接到** —— 它声明的出站主机（`egress`）。
- **设置** —— 它会向你索要的配置字段，含作用域（实例/用户）以及
  每一项是否为必填。
- **它发布的 AI 工具** —— 对声明了 `capabilities.mcpTools` 的插件：每个工具的名称、
  标题以及面向助手的描述，这样你在授予*之前*就能读到
  已连接的助手会被告知关于该插件的什么内容。
- **详情** —— 版本、下载大小、最低 Tourism-Team 版本、审核日期，以及
  指向源代码仓库和主页的链接。
- **版本** —— 每个已发布的版本（插件多于一个版本时列出）及其
  日期、签名盾牌和兼容性判定，每一个都有自己的 **安装 v{X}**
  按钮。这个 Tourism-Team 无法运行的版本会被解释说明（「需要 Tourism-Team {range}」），而绝不会被提供。

**已审核**徽章意味着 Tourism-Team 维护者扫描了那个确切版本的源代码
以查找恶意软件 —— **不是**说它运行良好或无害。它不是一项持续的
保证。请阅读访问列表和出站主机，而不只是描述。

## 安装插件

三种方式，都从 **管理 → 插件** 进入：

1. **从注册表。** 在**发现**中，打开一个插件并点击**安装**（也
   可直接在卡片上使用），它会取**这个 Tourism-Team 能运行的最新版本**。
   要取另一个版本，请使用详情
   模态框**版本**列表中的逐版本**安装 v{X}** 按钮 —— 有意安装一个不是最新
   兼容版本的版本会**暂停该插件的更新**，直到你恢复它们（见
   [更新插件](#updating-a-plugin)）。无论哪种方式，Tourism-Team 都会下载那个确切的版本，
   对照注册表校验其 SHA-256（若插件附带作者签名，也校验该签名），安全地解包它、
   重新校验清单并注册它 —— **处于未激活状态**。
   此时还没有任何东西运行。
2. **通过上传（手动加载）。** 把插件 `.zip`/`.tar.gz` 拖到面板上，或使用
   **上传**按钮。Tourism-Team 会用与注册表安装相同的硬性防护把它解压到暂存区（防路径穿越/防解压炸弹的解压、严格清单、无原生二进制文件 ——
   只有注册表的 SHA-256/签名校验不适用，因为没有注册表
   条目），并以**未激活**状态注册它。手动加载的插件会被标记为**手动加载**，
   未签名且未经注册表审核，**没有自动更新**，也没有「源代码
   仓库」链接。上传覆盖一个已存在的 ID 会先强制停止并停用旧
   代码，因此替换的代码绝不会在没有一次全新激活的情况下继续运行。
   （最大 50 MB，与 SDK 的 `pack` 上限相同。）
3. **从磁盘。** 把一个插件目录放入插件代码目录
   （`server/data/plugins`，或你的 `TREK_PLUGINS_DIR` 卷），然后点击**重新扫描**
   （或重启）。Tourism-Team 会发现它以未激活状态注册它。

## 激活插件

激活就是已安装行上的那个**开关**。打开它会授予你
已经审查过的权限并启动隔离进程；关闭它则
立即停止该进程，同时保留插件的数据。此后页面插件
出现在顶部导航中；小组件出现在仪表盘上。没有
单独的「激活」按钮，也没有第二次同意屏幕 —— 你在安装前
就已经审查过权限了。

## 插件与扩展之间的依赖

插件可以要求**其他插件**或**扩展**存在才能运行。
这在你**激活**时强制执行 —— 安装从不因依赖而失败，因此
你总是可以先安装、之后再解决。已安装行会把插件的
依赖显示为标签（缺失、超出范围或对应扩展已关闭时显示琥珀色）。

- **依赖的扩展已关闭** —— 激活会被阻止，并给出点名该
  扩展的消息。在 **管理 → 扩展** 中打开它，然后再打开该插件。在插件运行时
  把必需的扩展重新**关闭**会自动禁用该插件。
- **缺少它依赖的插件** —— 激活会打开一个**依赖对话框**，列出
  缺少的内容；每个都带一个**下载**按钮，从注册表获取最新的兼容
  版本（以及它自己的依赖），然后启用你的插件。一个
  已安装但*版本不对*的依赖则改为显示**更新**按钮。
- **依赖的插件已安装但处于关闭状态** —— 启用你的插件会
  **按顺序先自动启用它的依赖**。
- **禁用其他插件所依赖的插件也会禁用那些依赖者** —— 插件
  不能在依赖已经消失的情况下继续运行。

声明了依赖的插件还可以在运行时**互相调用函数并交换
事件** —— 始终由 Tourism-Team 中转，且只能沿着已声明的依赖（插件
无法触及它未声明依赖的插件）。见
[[插件开发|Plugin-Development#talking-to-other-plugins]]。

## 管理插件

每一行上的 **⋯** 菜单，按顺序为：

- **重启** —— 停止并重新派生进程（仅在激活状态下显示）。
- **实例设置** —— 管理员拥有的 `scope: "instance"` 字段，以及插件的
  实例作用域操作按钮（仅在它声明了其中之一时才显示）。机密
  字段保持掩码显示，只存储清单声明的字段，保存会重新派生
  正在运行的插件，使其读到新配置 —— 子进程只在启动时读取一次。
  见[插件设置操作](#plugin-settings-actions)。
- **查看错误日志** —— 插件自己的崩溃/失败请求日志。
- **允许的主机** —— 添加插件可以访问的主机，适用于与
  只有*你*才能说出名字的服务通信的插件（仅在插件的清单声明了
  `operatorEgress` 时显示）。见下方[允许的主机](#allowed-hosts)。
- **更换版本** —— 切换到该插件的任何已发布版本（仅限注册表安装）。
  见[固定与回滚](#pinning-and-rolling-back)。
- **源代码仓库** —— 打开插件的 GitHub 仓库（仅限注册表安装）。
- **报告问题** —— 打开该仓库的 issue 跟踪器（仅限注册表安装）。
- **删除** —— 在确认后卸载：它会停止插件、移除其代码，
  **并删除其全部数据**。此操作无法撤销。

## 允许的主机

插件的出站主机通常在其清单中固定，你在安装时就同意了它们。
但与**自托管服务**通信的插件 —— 一个 Gotify、一个 ntfy、一个
Uptime Kuma —— 在发布时无法知道*你的*主机名。这样的插件声明
`operatorEgress`，而由你自己提供主机。

安装之前，详情模态框会在*连接到*下方用一个**「+ 你添加的主机」**胶囊标记这类插件。
在已安装行上，它会显示一个**添加允许的主机**标签
（你添加之后为 **{n} 个允许的主机**）。打开 **⋯ → 允许的主机**，
添加主机名（例如 `gotify.mydomain.com`）。Tourism-Team 会重启该插件，使其读取
新列表。

这*不会*让任何人能够做的事：

- **从未请求过它的插件永远无法被赋予主机。** 只有清单声明了
  `operatorEgress` 的插件才有资格，因此你在安装时给出的同意仍然
  限定了什么是可能的。
- **只有你 —— 管理员 —— 才能扩展出站范围。** 终端用户永远无法添加主机，即使
  插件的凭据由他们自己提供。
- 主机的校验方式与清单出站项相同：不允许裸 `*`、不允许整段 TLD 通配符、不允许携带 scheme。
  移除一个主机，插件会立即失去它（它会再次重启）。
- 卸载会丢弃这些主机，因此之后重用该 ID 的插件无法继承它们。

如果该服务与 Tourism-Team 运行在**同一台机器或 LAN** 上（一个 `localhost` 或 `192.168.x.x`
地址），你还需要 `TREK_PLUGIN_ALLOW_PRIVATE_EGRESS=on` —— 插件默认不得访问
私有地址。这会放松*每一个*已安装插件的策略，因此
只有在你信任它们全部时才启用它。

## 审查插件做了什么 —— 活动日志

每个用户都能确切看到插件**以他们的名义**做了什么。在
**设置 → 插件**下，**活动日志**列出某个
插件在代表你行动时所做的每一项经主机中转的操作 —— 跨所有插件，最新的在前：它读取的每一次旅行或
费用、写入的每一个地点、Tourism-Team 代它发出的每一次出站调用。

这是 Tourism-Team 防篡改（哈希链式）插件
审计面向用户的那一半：同一条链可以通过管理员 API 按插件读取
（`GET /api/admin/plugins/:id/audit`），而这个视图
**从不设管理员门槛** —— 任何人都可以审查别人用自己的数据做了什么。正是它
让插件刻意宽泛的读取授权对数据被读取的那个人负责。每个
授权究竟允许什么，见 [[插件权限|Plugin-Permissions]]。

## 更新插件

当注册表列出更新的版本时，行上会出现一个**更新到 vX.Y.Z** 胶囊，
并且一条**全部更新**提示条会汇总有多少可用 —— 除非以下两种情况之一成立。
一个 `trek` 范围是本主机无法满足的更新版本会显示一条信息性的
**「v{version} 可用 — 需要 Tourism-Team {range}」** 行，并且刻意永远不显示
按钮：解决办法是升级 Tourism-Team，而不是做一次会被拒绝的安装。而一个更新被
暂扣的插件则改为显示 **「更新已暂停在 v{version}」**，并带一个**恢复更新**链接
（见下文）。

更新会替换为新代码，并默认透明地在新代码上重启插件。
但如果新版本声明了**更多权限或新的出站主机**，
Tourism-Team 会安装新代码并**让插件保持关闭**，然后显示一个
**重新同意对话框**，准确列出新增的权限和主机。只有在你批准之后
插件才会再次运行 —— 更新绝不能悄悄扩大插件的权限范围。选择「稍后」会保留新代码已安装
但处于未激活状态。

### 固定与回滚

**⋯ → 更换版本**会列出注册表安装的插件的每个已发布版本，包含
其日期、签名盾牌和兼容性判定，并切换到你选定的那个；不兼容的版本会被
解释说明，而绝不会被提供。切换到**更低**的旧版本会
先要求确认 —— 插件已存储的数据会保留下来，而旧代码可能无法
理解它。

有意切换到一个不是最新兼容版本的做法会设置一个**更新
暂扣**，这样你本意的回滚就不会被更新胶囊反复催促：该行会显示
「更新已暂停在 v{version}」，并带一个**恢复更新**链接，点击它会让
插件回到正常的更新流程。以任何方式重新落到最新兼容版本，
都会自行解除该暂扣。

## 构建你自己的插件

插件使用**插件 SDK** 及其 `trek-plugin` CLI 构建。该 CLI
把一个已构建的插件目录变成可发布的产物和可直接发起 PR 的
注册表条目，因此你永远不必手工计算 SHA-256 或手写注册表 JSON：

| 命令 | 作用 |
|---|---|
| `trek-plugin validate [dir]` | 在本地运行清单 + 布局检查（注册表 CI 的一个子集，后者还会通过网络校验发布版本、产物的 SHA-256 和 README）。 |
| `trek-plugin pack [dir] [--out plugin.zip] [--json]` | 按安装器的确切布局构建 `plugin.zip` 并打印其 SHA-256 + 字节大小。拒绝原生二进制文件；`docs/` 有意不打包（商店从你的仓库获取截图）。 |
| `trek-plugin entry --repo <o/n> --tag <vX> [--zip z] [--merge entry.json] [--out f]` | 生成注册表条目 —— `commitSha`、`downloadUrl`、`sha256`、`size` 以及清单的 `trek` 范围（原样）全部填好。`--merge` 会把新版本前插到用于更新的现有条目前面。 |
| `trek-plugin release [dir] --repo <o/n> --tag <vX>` | 一步到位：`pack` → 创建 GitHub release → 打印条目。 |

通过 `npx trek-plugin-sdk …` 运行它们。SDK 和清单见
[[插件开发|Plugin-Development]]，注册表 PR 流程见
[[发布插件|Plugin-Publishing]]。任何唯一的 slug 都可以 —— 只有 `registry`、`install` 和 `rescan`
会被拒绝（它们会与管理员 API 路由冲突）—— 而一个 `id` 始终绑定到
最先注册它的那个 GitHub 所有者，因此
没有人能重新指向一个已存在的插件。条目可以选择携带一个作者
签名密钥（`authorPublicKey` + 每版本一个 `signature`），用于在 SHA-256 固定之外
做离线签名校验。已签名插件的密钥只会通过
维护者批准的轮换而改变；已经装有该插件的实例届时会显示
`SIGNATURE_KEY_CHANGED` —— 并附上两个密钥指纹，以便你
通过带外方式向作者核实新密钥 —— 并在你重新信任
新密钥之前暂停该插件的更新。
