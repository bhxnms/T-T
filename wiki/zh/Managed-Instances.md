# 托管实例

**托管实例**是别人代你运行的 Tourism-Team 部署 —— 一项托管服务、一个公司内部部署、一个共享实例。它是一种独立的运行模式，而不只是一套配置。

该模式在服务器上通过 `TREK_MANAGED=true` 启用。它改变管理员能做什么，因为在托管实例上，持有管理员账户的人并不是运维服务器的人。

## 改变了什么

在托管实例上，某些管理界面被 **扣下** —— 服务器直接拒绝它们，而不是在界面中隐藏，因此无法通过直接调用 API 来绕过限制。它们都是其取值属于运维安装方的那类设置：

- **存储后端**及其凭据
- **Cloudflare 隧道**配置
- **备份**计划与恢复 —— 备份在托管安装上运行于卷外，因此客户自建的计划会与真正的那个相互竞争
- **发布渠道与更新检查** —— 由运维方决定实例何时升级
- **SMTP、OIDC 以及对外集成**中凭据属于运维方的那些
- **插件侧载与链接**
- 注册到运维方自己账户的 **实例 API 密钥**（地图、天气、大模型等）

这个模式是一以贯之的：凡是使用客户自己的账户会让运维方的安排变得无从交代的地方，或者两方会重复安排同一项作业的地方，都归运维方。

## 什么仍留给管理员

凡是关于 *这个实例的用户如何工作* 的一切都仍然可用：

- 用户账户与邀请
- 分类与打包模板
- 扩展开关，包括协作功能
- 按用户生效的默认设置
- 审计日志
- 实例自有渠道的通知配置

其意图是：公司可以为自己的员工运行 Tourism-Team，而员工的管理员仍然可以塑造工作区 —— 同时无法把实例指向另一个数据库或改掉它的邮件出口。

## 用户看到什么

从用户的角度看，托管实例与普通实例没有区别，只有三处不同：

- **发布提示与支持提示被抑制。** 当读者已经向运行实例的人付费时，请他们资助项目的提示毫无意义，而 bug 报告应该交给运维方而不是上游。
- **有些集成是预配置的**，用户无法编辑。
- **关于页面被精简** —— 源码链接和版本保留，因为许可证要求向网络用户提供源码，但那些面向自托管者的部分被移除。

## 运维一个托管实例

如果你运维着一个托管实例，想覆盖某个被扣下的设置，你要在实例的环境里设置它，而不是通过界面。环境变量的取值优先于数据库中存储的任何内容，这也是客户侧的改动无法悄悄生效的原因。

> **关于信任的说明。** 托管管理员仍然可以读取他所管理实例的数据 ——
> 这就是管理员账户的含义。该模式限制的是他们能*重新配置*什么，而不是他们能看见什么。
